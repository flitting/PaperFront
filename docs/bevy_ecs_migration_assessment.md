# Bevy / ECS 迁移可行性与性能收益评估

日期：2026-10-03（Australia/Sydney）。

**状态：基于最终同一 Linux Release 构建完成评估。本文没有创建或运行 Bevy 移植项目，也没有把假设倍数标成实测结果。**

技术上可迁移。当前证据支持继续优化 Godot 中的高频数据访问、显示批量提交和 CPU/GPU 调度；完整换引擎的收益还需要同画质、同规则、同硬件的原型证明。Bevy 的 ECS 可提供清晰的组件数据布局与并行查询工具，但不会自动减少树木三角形、阴影或全屏像素的 GPU 成本。

## 1. 本项目已有证据

当前四阵营八方夹具是 640×640 地图、800 单位（640 地面 / 160 飞机）、160 建筑，重锤/正典/铁钉/天翼各两个独立所属。伤亡按真实规则处理，测试预备队补充新 ID，30 Hz 仿真保持不变。它不包含八套完整经济战略 AI。

以下为最终构建及明确标注的历史对照证据；完整结果见 [最终验收报告](performance_640_results.md)：

| 范围 | 数据 | 证据 |
|---|---|---|
| 常见单位状态机，串行 CPU 对照 | GDScript 平均 18.35 ms/tick → 原生 13.94 ms/tick，约减少 24%；P99 22.32 → 17.55 ms | `artifacts/performance_640/native_units/cpu_script.json`、`cpu_native.json` |
| 四阵营八方，1080p / 100%，最终发行包 120 秒 | 平均 42.24 FPS，最低秒级 38.79，P99 换算 30.16 FPS | `artifacts/performance_640/phase19/stress_120s.json` |
| 同一实际渲染场景的耗时均值 | 仿真 11.704 ms/tick；预备队 0.862 ms/tick；显示 4.944 ms/frame；主逻辑 5.301 ms/frame；GPU 22.197 ms/frame | 同上 |
| 同一最终构建的原生全屏 | 3072×1920 / 100%，30 秒平均 34.06 FPS、最低秒级 33.62、P99 换算 28.49 | `artifacts/performance_640/phase19/fullscreen_30s.json` |
| 玩法与显示等价性 | 两组 300 tick、全部兵种、存读档的 6,002 项对照一致；节点架构调整的固定图像逐像素一致 | `native_units/equivalence_all.log`、`four_factions/pose_image_comparison.json` |

这说明部分收益来自消除解释执行和重复数据访问，已有一部分收益无需切换引擎就能获得。CPU 与 GPU 同时有成本，不能把某一 CPU 子程序的加速比直接当作整体 FPS 加速比。上述阶段计时使用墙钟耗时，包含操作系统调度影响；它们不是硬件计数器测得的独占 CPU 周期。

## 2. ECS 能改善什么

本游戏的 `entities` 当前主要是动态字典。位置、生命、朝向、命令、机场和武器属性频繁按键读取，临时数组与跨脚本调用也会产生开销。ECS 重构可把高频字段拆为连续组件列，把稀有状态放到单独组件，使索敌、计时器、空间索引准备和显示提取按同类数据批量处理。

Bevy 的 `Query` 提供串行与并行迭代接口，包括 `par_iter` / `par_iter_mut`。这只是并行执行能力，收益仍取决于查询粒度、数据访问冲突和系统实际工作量。[官方 Query 文档](https://docs.rs/bevy/latest/bevy/ecs/system/struct.Query.html)

仿真必须明确配置为 30 Hz。`FixedUpdate` 可在一个显示帧中执行零次、一次或多次；换用这个调度并不会自动消除过载后的补算。[官方 FixedUpdate 文档](https://docs.rs/bevy/latest/bevy/prelude/struct.FixedUpdate.html)

需要保持本项目特有的顺序语义：相等距离目标的选择、同 tick 移动后的位置可见性、碾压、资金不足时维修优先级、机场容量分配、伤害汇总和死亡补位。建议先产生只读查询结果，再以稳定实体 ID 和明确阶段提交变更；但若改为完全读取 tick 开头快照，会改变当前“前一个单位移动后，后一个单位可见新位置”的语义，因此仍须做逐 tick 等价校验，不能直接把循环换成无序并行迭代。

## 3. 可以讨论的提升水平

尚未移植本游戏到 Bevy，所以**目前没有可报告的 Bevy 实测提升倍数**。以下仅是用最终实测均值 11.704 ms/tick、30 tick/s 做的敏感性分析；倍数是输入假设，不是预测。

| 假设仿真执行加速 | 假设仿真耗时 | 每秒仿真计算时间预算 | 相比该阶段释放的时间预算 |
|---|---:|---:|---:|
| 1× | 11.704 ms/tick | 351.12 ms/s | 0.00 ms/s |
| 2× | 5.852 ms/tick | 175.56 ms/s | 175.56 ms/s |
| 4× | 2.926 ms/tick | 87.78 ms/s | 263.34 ms/s |
| 8× | 1.463 ms/tick | 43.89 ms/s | 307.23 ms/s |

这些数值只描述仿真部分，显示更新、渲染提交、特效、UI、预备队和 GPU 仍要执行。若 GPU 成本固定在最终约 22.197 ms/frame 且成为瓶颈，对应约 45.1 FPS 的预算量级，与本机当前 42.24 FPS 平均值相差约 6.7%。这不是迁移收益预测，也不是跨引擎的硬件上限：释放 CPU 压力可能改变共享功耗/内存压力，换渲染器也会改变 GPU 成本，须重新实测。该换算只用于判断潜在限制，不是对 Bevy 的 FPS 保证，也不证明 P99 达标。

仅在假设仿真和显示都串行执行于同一线程时，可以采用 `F_cpu ≤ (1000 - 30 × S) / R` 做预算筛查；当前重叠路径不满足这个前提。式中，`S` 是仿真均值，`R` 是每个显示帧剩余串行工作的均值。缺少完整的 `R`、并行重叠和驱动等待信息时，不应给出确定总帧率。各阶段 P95/P99 不能相加，也不能线性缩放后当作整体尾帧预测。

要把假设变成可信范围，未来原型至少须在同机同电源状态下比较：相同存档/命令轨迹的纯仿真、真实固定 800/160 混战、1080p 和原生全屏，且输出质量、内部像素、伤亡/补给、人口和仿真/墙钟比均一致。必须同时报告均值、最低秒级、P99 和最大帧。

## 4. 三种方案

| 方案 | 主要收益来源 | 需要移植的内容 | 对当前目标的判断 |
|---|---|---|---|
| Godot + 更完整的原生数据核心 | 减少字典/脚本开销、批量提交、连续数据 | 高频规则与显示数据结构，保留现有渲染和 UI | 当前最直接，已有等价测试和阶段实测支持 |
| Godot + Rust / bevy_ecs 仿真模块 | 组件布局、受控并行、可独立测试的模拟 | 仿真核心、命令/事件和显示快照边界、GDExtension 接口 | 可作为后续架构方案；逐实体往返动态字典会抵消收益，应批量交换数据 |
| 完整 Bevy 引擎 | 同时重做仿真、调度和渲染架构 | 规则、地图构建、渲染、着色器、输入/UI、音频、存档和工具 | 可行但范围最大；仅为解决当前帧率问题，证据还不足以支持直接整体迁移 |

Bevy 0.19 的官方说明展示了大型场景渲染改进、连续查询访问和渲染调度调整；这些是评估候选能力的依据，官方示例的性能不能套用到本游戏。[Bevy 0.19 发布说明](https://bevy.org/news/bevy-0-19/)

## 5. 迁移范围与主要成本

第五阶段检查中，仅仿真、世界显示、地形、主控制器、基础模型、两个扩展阵营、HUD 和音频这九个源文件合计约 12,435 行，尚未计入测试、Wiki、寻路工作线程等模块。代码行数不是工期，但说明完整迁移涉及整个运行链。

- **玩法核心**：所有 56 单位、56 建筑与 47 武器的规则、命令、工程兵施工、运输、机场、电力、经济、八所属和旧存档状态均需保持。可复用 JSON 规则与现有测试场景，不能直接复用 GDScript 执行逻辑。
- **美术与渲染**：当前大量模型与地形由 Godot 过程代码生成，`.res` / `.scn` 不是可直接视为跨引擎资产的接口。可导出几何或迁移生成器；必须重建纸片五动作、固定镜像边界、炮塔/炮口、所有权色、LOD、批次、粒子、阴影与景深。
- **材质观感**：Godot 空间着色器、颜色空间、光照和后处理需转换到 Bevy 的材质/渲染接口。不能仅替换默认 PBR 材质就声称视觉等价；应复用固定画面对照、近景轮廓和动态战斗检查。
- **输入与 UI**：中文字体、纸板 HUD、Wiki、生产卡、微缩图、镜头与世界点选、全屏/缩放坐标都需要重新集成。字体存在并不等于字号、布局和点击区域相同。
- **音频和存档**：音频素材可复用，播放池、语音字幕、优先级和音量逻辑仍需移植；当前 Godot Variant 存档需要兼容读取或显式转换器。
- **维护**：版本升级可能触及渲染与插件接口。应锁定版本并保留原画面和行为基线，具体 API 变化以官方迁移指南为准。[0.18 → 0.19 迁移指南](https://bevy.org/learn/migration-guides/0-18-to-0-19/)

Godot 内的受控仿真/渲染重叠已通过 6,002 项线程状态对照、完整回归和实际窗口生命周期检查，并在第六阶段默认启用。同一最终构建的普通场景达到最低秒级 81.62 / P99 换算 67.26 FPS；八方 120 秒长测达到最低秒级 38.79 / P99 换算 30.16 FPS。这是无需更换引擎获得的实测收益，不能计作 Bevy 收益。

第九阶段的慢帧诊断进一步显示：120 个超预算间隔中，118 个只完成了一个模拟 tick。多 tick 补算仅解释少数最大尖峰，当前 P99 仍涉及单 tick 负载、显示更新及渲染等待的组合。即使 ECS 大幅加速仿真，也必须验证整个显示路径和 GPU 的尾部成本。证据：`artifacts/performance_640/phase9/stress_airfields_1080.json`。

第十二阶段另定位到批次上传的同步 GPU 回读：通过初始化 CPU 缓存，该次慢帧中的上传阶段峰值从此前约 14–19 ms 降到最高 2.217 ms。这个案例说明，整帧卡顿还受渲染 API 的数据归属和同步方式影响；更换 ECS 本身不等价于消除这些等待。证据：`phase12/stress_world_trace.json` 与 `phase12/stress_cache_init.json`。

## 6. 最终判断

当前 CPU 工作仍显著：八方模拟约 11.7 ms/tick，显示更新约 4.94 ms/frame，且长测存在少数 CPU/系统调度尖峰。因此未来若扩大到更多单位或更复杂 AI，ECS/连续数据布局有研究价值；原生执行和受控调度也已在 Godot 内带来了实际收益。

本次规定的 1080p 60/30 FPS 基准已经通过，八方 P99 余量仅约 0.18 ms，原生全屏 P99 换算仍是 28.49 FPS。GPU 均值已占据主要帧预算，不能据此承诺仅把仿真搬到 Bevy 就能大幅提高平均 FPS。保留当前 Godot 渲染/界面、先验证独立数据化仿真原型，比直接整体换引擎更容易隔离收益和保护现有规则/画面。

如未来立项，先固定相同规则、命令轨迹、可见几何、输出/内部像素和当前机器，测原型的纯模拟、实际 GPU 混战及尾帧，再决定是否扩大迁移范围。上表 2×/4×/8× 是参数情景，最终没有本游戏的 Bevy 实测倍数。

本任务只交付此评估文档，未执行引擎迁移。
