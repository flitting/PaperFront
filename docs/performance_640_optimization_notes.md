# 640 地图与八方压力性能：优化目标、观察及待验证问题

> 后续视觉恢复：用户已要求撤回模型精度取舍，不再以性能为约束。当前版本恢复完整模型并修复景深，见 [视觉恢复记录](visual_fidelity_restoration.md)。下文为已关闭优化任务的历史过程与成绩。

记录日期：2026-10-03（Australia/Sydney）。

**最终验收：规定的 1080p 常态 60 FPS、八方 120 秒混战 30 FPS 两项基准均通过。原生全屏另行报告，P99 换算低于 30 FPS。最终结果、限制、审计和交付说明见 [最终验收报告](performance_640_results.md)。**

以下第 1–7 节是历史要求与早期失败记录，第 8 节及后续阶段保留全部优化过程。历史“当前”“待验证”“未导出”等措辞仅指当时阶段，不能覆盖最终报告的结论。

## 1. 当前需要达成的关键目标

| 优先级 | 目标 | 后续验收重点 |
|---|---|---|
| P0 | 常态游戏达到 60 FPS | 640×640 地图、1920×1080 输出；现有常态夹具为 96 单位、24 建筑，含 8 架飞机。检查尾帧，不能只看平均值。 |
| P0 | 八方持续混战达到 30 FPS | 640×640；8 个独立势力，每方 20 建筑、100 单位；每方 80 地面单位、20 飞机，共 800 单位、160 建筑。按最新要求纳入重锤、正典、铁钉、天翼四个完整阵营模板，各由两个独立势力使用。 |
| P0 | 降低密集战斗的 CPU 尾帧 | 针对索敌、支援维修、空间索引和机场占用统计；保持真实伤害、死亡、返航补给及单位更新频率。 |
| P0 | 控制特效、尸体和模型创建成本 | 验证最新性能档的粒子预算、短尸体、模型池及轻量材质是否有效，及是否产生视觉或交互错误。 |
| P1 | 明确画质和分辨率取舍 | 用户允许部分牺牲建模及渲染质量。1920×1080 为当前优化基准；3072×1920 原生全屏保留为对照。分别记录输出和内部 3D 像素。 |
| P1 | 降低超大地图启动与交互卡顿 | 分开记录地图生成、导航初始化、地形构建、模型预热及首次开火；检查树冠点选、镜头移动和缩放。 |

| P1 | 条件性的 Bevy/ECS 迁移评估 | 优化结束时若 CPU 压力仍明显，以最终热点与测量证据编写文档，评估 ECS 数据布局、调度、原生执行、渲染和移植成本。收益须分解可计算的理论范围与尚待原型验证的部分；本任务不执行迁移。 |
| P1 | 验证并交付可复现的发行包 | 当前源码完整回归、离线 LOD 资产验证、Linux release 导出，再在实际导出的程序中复测。 |

帧时间预算：60 FPS 对应 **16.67 ms/帧**，30 FPS 对应 **33.33 ms/帧**。内部已采用“最低 1 秒 FPS”和 `1000 / P99 帧耗时` 两项共同检查，另报告最大单帧耗时。这一判据比只检查平均 FPS 更严格；`1000 / P99` 是本文报告中的尾帧换算指标，不等同于所有软件通用的“1% low”算法。

建议后续把八方纯模拟的 P99 压到约 20 ms 以下，为显示更新及其他工作留出余量。该值是优化预算，尚未实现。CPU、GPU 和渲染阶段可能重叠，不能把各阶段分位数简单相加推算 FPS，仍须以实际呈现帧间隔验收。

## 2. 测试条件与场景边界

- CPU：Intel Core Ultra 9 185H。
- GPU：Intel Arc Graphics（MTL），Vulkan / Forward+，Godot 4.6.2。
- 当前内屏：3072×1920，约 60 Hz。
- 已有 GPU 测试关闭垂直同步，记录实际帧间隔；未改变游戏的 30 Hz 模拟频率。
- 音频逻辑启用，测试进程输出总线设为静音，避免持续战斗噪声。
- GPU 测试串行进行，热身 8 秒后采样 20 或 30 秒。启动和热身成本另算，不能用稳定阶段结果声称首次加载也流畅。
- 普通场景允许真实伤亡和生产，采样时人口会下降。八方场景通过**测试预备队**补充真实阵亡单位，维持每方 100 单位；保留伤害、死亡事件和新单位 ID，不给幸存者回血。
- 八方有独立规则 ID、所属、资金、生产订单、敌我关系和机场保障。六个测试势力复用现有两派的陆空模型模板，以八种识别色区分；这不等同于新增六套完整派系美术与剧情。
- 决策采用夹具设定的攻击移动及补充安排，未运行八套完整经济战略 AI。因此该测试覆盖密集战斗负载，不能替代多人策略或长期经济平衡验证。

## 4. 已知 CPU 观察

最终八方 CPU 夹具保持 800 存活单位，按 30 Hz 推进。以下为短时串行诊断，不包含实际 GPU 绘制。

| 指标 | 接触快照优化前 | 优化后 |
|---|---:|---:|
| 纯模拟平均耗时 | 49.06 ms/tick | 32.54 ms/tick |
| 纯模拟 P95 | 61.43 ms/tick | 37.16 ms/tick |
| 纯模拟 P99 | 75.25 ms/tick | 48.13 ms/tick |
| 预备队补位平均耗时 | 2.16 ms/tick | 0.97 ms/tick |
| 预备队补位 P95 | 9.65 ms/tick | 3.14 ms/tick |

改善后仍超过适合 30 FPS 的模拟预算。分辨率降低能减轻 GPU 压力，**无法解决这部分 CPU 耗时**。

明确观察如下：

1. **索敌是已确认的大热点。** 20 tick 的细分诊断中，索敌累计耗时由约 766.53 ms 降到 139.94 ms；武器权限函数调用数由 128484 降到 14957。已采用同 tick 的位置／所属／域快照、中心桶优先和距离下界剪枝，并保持精确最近目标与相等距离规则。
2. **支援维修成为当前突出的剩余热点。** 20 tick 中约 143.34 ms，即约 7.17 ms/tick。当前代码仍逐个地面单位遍历所有维修站，并重复读取所属和装甲属性；按所属分组、预读取半径与速度的优化在停止时尚未完成。
3. **空间索引准备仍有成本。** 对应细分诊断约 4 ms/tick，需继续区分重建、快照写入、缓存失效和数据分配。
4. **机场占用反复全表统计影响补位。** 已改为通过合法生成、死亡、归属和转场流程维护缓存；仍须在飞机大量伤亡和机场被毁的长段测试中验证。
5. **大量炮弹并非当时最大的 CPU 热点。** 该 20 tick 诊断中，弹丸阶段约 0.39 ms/tick、局部爆炸查询约 0.27 ms/tick；不能据此排除更长或不同战况下的瓶颈。

细分调用计时有额外开销，属于定位证据，不能与普通 CPU 报告混用作 FPS 换算。原先另有 256／512 坦克诊断夹具，其数值不能代替最终八方陆空混战。

已将临时诊断报告保存到项目内：[CPU 优化前](../artifacts/performance_640/diagnostics/eight_pressure_cpu_before_contacts.json)、[接触快照优化后](../artifacts/performance_640/diagnostics/eight_pressure_cpu_contacts.json)、[细分诊断](../artifacts/performance_640/diagnostics/eight_pressure_sections_contacts.json)。

## 6. 潜在问题及后续必须确认的事项

- **缓存失效和相等距离规则。** 生成、移动、死亡、俘获、装卸、施工完成、机场失守和载档都能改变派生缓存。部分等价检查通过不代表所有组合场景已覆盖。
- **模型池状态残留。** 需验证复用后的所属牌、材质、血条、镜像、炮塔、飞行高度、死亡姿态和拾取锚点，尤其切换画质、俘获和脚手架完成时。
- **视觉预算的代价。** 粒子及尸体上限会减少混战反馈；轻量材质、远 LOD、少描边和无景深会改变观感。应保留炮塔／机身轮廓和八色识别，并实际截图审查。
- **离线资产与 release 一致性。** 索引资源、模板顶点顺序、法线修复及源码哈希须一致。编辑器能够运行不能证明导出的程序使用了相同资产或取得相同 FPS。
- **压力夹具的代表性。** 固定人口预备队带来正常对局未必具有的高频死亡／重建；它是刻意更重的工作负载，应明确记录。建筑目前主要记录初始数量，长段测试还应记录每方最低存续建筑数及陆空配额。
- **AI 与长期战争。** 当前八方策略决策并非正式八方 AI。还需持续交战、返航／补给、机场损毁、运输、修桥、脚手架和经济队列的组合验证。
- **冷启动与输入尾帧。** 640 地图生成已测约 2.7 秒，纯模拟初始化曾约 8.1 秒；这些不是完整启动时间。首次模型创建、开火、全屏切换、缩放及树冠点击的卡顿需单独量化。
- **分辨率报告准确性。** 1920×1080 与 3072×1920 不可混用；若全屏输出保持高分辨率、内部 3D 采用缩放，必须写出具体内部像素和渲染比例。
- **测试版本和并行改动。** 项目中另有阵营／素材扩展；部分旧测试和基准是在不同目录规模、不同源码阶段取得。后续应冻结并记录源码、规则、资产哈希，再做可比较测试，避免覆盖并行工作的改动。
- **机器状态和测量范围。** 使用同一电源／性能模式、分辨率、场景、镜头及画质；GPU 测量期间避免并发重 CPU／GPU 测试。不能把本机短段结果推广为所有硬件或任意规模的 FPS 保证。

## 7. 建议恢复后的顺序

1. 冻结当前版本并记录哈希，确认最新源码可编译；先补支援维修分组优化及严格等价检查，再复测空间准备和索敌。
2. 用相同八方夹具分别测纯模拟、预备队补位和显示更新，确认每方人口／陆空组成及实际模拟时间没有悄悄下降。
3. 在 1920×1080 复测最新性能档的固定 800／160 压力，以及常态均衡／性能档；记录平均、最低秒级、P95／P99、最大帧和各阶段耗时。
4. 根据实测结果再决定进一步模型、材质或渲染比例取舍。不要先堆叠未测的优化；3072×1920 原生全屏继续作为明确标注的对照。
5. 跑统一功能回归，导出 release，在导出程序中复测相同场景，核对资产与日志，随后才更新运行包和达标结论。

**停止时结论：普通 1080p 的平均和秒级性能已有改善，严格尾帧目标仍未满足；最终八方 1080p 30 FPS 未验证，原生高分辨率全屏第一轮明显未达标。**


## 8. 恢复优化（2026-10-03，进行中）

当前源码没有 Git 元数据。修改前已保存 `artifacts/performance_640/resumed/baseline/source.tar.gz` 和 `sha256.json`，避免覆盖新增阵营工作。原正式独立程序尚未替换；中间发行测试包位于 `artifacts/performance_640/resumed/build/`。

- 素材导入：新增阵营图片虽已存在，但未完成 Godot 导入，首次无头性能工具未检查失败，生成了空场景报告。`baseline/cpu.json` **无效**（0 单位、未推进模拟），不得用于性能比较。已导入素材并让 CPU 工具在规则或人口不合法时退出。有效 CPU 基线为 `baseline/cpu_imported.json`。
- CPU：维修站按所属分组并预读服务属性，保留单位遍历顺序与扣款优先级，80 组逐项等价检查通过。空间快照改为直接一遍构造；武器权限复用 tick 内的域掩码。缓存检查 260 项通过。
- GPU 分层：`render_layers.json` 与 `render_detail.json` 是固定场景的渲染诊断，不能作为游戏 FPS。内部宽高各减半几乎无收益；隐藏树干/根部层令 GPU 中位数约从 38.4 降到 22.5 ms。原树干根饰每棵 1,638 三角形，几何和阴影重复绘制是一个主要热点。
- 树干 LOD：45m 内保留完整原模型，远景保留主干与三个根部石块位置，减少根饰微小几何。近远层均保持每棵树，并响应同一毁树事件。树冠原始几何未变；已重新烘焙验证资源哈希。场景性能 14、点选/毁树 14、树冠法线/几何 10 项检查通过。
